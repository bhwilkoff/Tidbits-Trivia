## 3. What was fixed this session

### Android crash (Play "Broken Functionality", version code 85 AND 75)

Root cause, measured not guessed: `AppRoot` loaded **all eight JSON shape sets at
app boot**, each via `readText()` + `parseToJsonElement()` (whole file as a
String, then a full JSON DOM, before any mapping). Those assets grew **2.5x
between the two Play builds** — 7.1MB at vc80 to 17.5MB, with `typeanswer.json`
alone going 4.27MB → 13.72MB on 2026-08-02. Same OOM class Decision 049 fixed for
the corpus, re-formed around the shape sets.

Fix: each set loads on first use (`JsonQuestionSet.ensure()`, app context held
from `Application.onCreate` like Billing/QuizStore). Corpus stays eager — it is
sqlite-backed, keeps only ids, and the first screen needs it.

Measured on the **release** APK:

| | before | after |
|---|---|---|
| Launch Java heap | 71–98 MB | **19.5 MB** |
| TOTAL PSS | 104–133 MB | **63 MB** |
| After 900 monkey events | — | 10.7 MB, **0 fatals** |
| Release APK | 42.8 MB | **29.1 MB** |

Also removed 55MB of `corpus.json` that ships in the APK but **no Android code
reads** (only `corpus.sqlite` is). `sync_shared_assets.sh` now excludes it.

**The trap in that change**, worth knowing if it ever regresses: two paths read
the sets — `filled()` for normal play and `sourceType()` for Trivia Night, which
**bypasses `filled()` entirely**. Miss the second and night rounds come back empty
("No questions yet", a bug this codebase has shipped before). All 13 modes were
driven individually through the autoplay hook to confirm: 13 pass, 0 failures.

```bash
# how the mode sweep was run
adb shell am start -n com.tidbitstrivia.app.debug/com.learningischange.tidbitstrivia.MainActivity \
  -e tidbits_autoplay "TYPE_ANSWER:mixed"
```

### Other fixes shipped this session

- **Web layout**: the `>=720px` rule centred `.main`/`.results`/`.game` but not
  `.topbar`, so the header ran full-bleed while content was centred; and because
  `.main` IS the scroll container, capping its width also capped the wheel target.
  Content now centres via `padding-inline`; header and content share `--content`.
- **Web first-visit double load**: `sw.js` installs with `skipWaiting()` and
  activates with `clients.claim()`, so on a first visit the new worker claimed the
  open page, fired `controllerchange`, and `index.html` **reloaded itself**. Every
  first visit loaded twice — the flash under the onboarding dialog. Now only
  reloads if the page **had** a controller (a genuine update).
- **Refund policy** published at `/refunds.html`, linked from the paywall footer,
  apps footer, terms and support.
- **Android App Links**: `assetlinks.json` had only the upload key; the **Play App
  Signing** fingerprint was missing, so links verified only for locally-built
  installs. Both are live and Google's Digital Asset Links API returns 2 statements.
- **APNs**: no new key needed — APNs was enabled on the **existing** `QT5PJV96B7`
  key, so the `.p8` already on disk works. All four `APNS_*` GitHub secrets set.

## 5. Gotchas that cost real time — don't rediscover these

**Play**
- **The internal track generates NO pre-launch report.** Google's rejection email
  says "use test tracks", which reads as internal. It must be the **default closed**
  (`alpha`) or open track. Hours were lost waiting on a report that could not exist.
- **`submit-play.sh` printing "Play refused to auto-submit this edit" is real.**
  `tools/play-publish.py` falls back to `changesNotSentForReview=True` because
  Google 400s the auto-submit path **for any app with an open policy issue**. The
  release still lands on the track (API confirms `completed`) but the app-level
  changes sit under "Changes not yet submitted for review".
- **"Submit N changes for review" is ALL-OR-NOTHING** and the list is app-wide — it
  contained a **Production / start full rollout** row. Per-row "Save for later" was
  **disabled** ("changes that affect your whole app").

**Apple**
- `READY_TO_SUBMIT` means **never submitted**. Check what a review submission
  actually *contains*, not the product's own state:
  ```bash
  python3 tools/asc.py get "v1/apps/6782202277/reviewSubmissions?limit=10"
  python3 tools/asc.py get "v1/reviewSubmissions/<id>/items?limit=20"
  ```
  Item ids are base64 → `submission|type|entity`. Type **6** = appStoreVersion,
  **17** = IAP version, **18** = subscriptionVersion, **19** = subscription group.
- **Attaching a subscription to a submission uses `subscriptionVersion`**, and it
  takes a subscription **version**, not the subscription. Found by probing names
  until the error changed from *"not a relationship"* to a **type** mismatch:
  ```bash
  python3 tools/asc.py post v1/reviewSubmissionItems '{"data":{"type":"reviewSubmissionItems",
    "relationships":{"reviewSubmission":{"data":{"type":"reviewSubmissions","id":"<sub>"}},
    "subscriptionVersion":{"data":{"type":"subscriptionVersions","id":"<ver>"}}}}}'
  # versions: python3 tools/asc.py get "v1/subscriptions/<id>/versions?limit=5"
  ```
- **A new subscription GROUP must be submitted together with at least one
  auto-renewable subscription from inside it** — that is the *"New subscription
  groups must be submitted with an auto-renewable subscription"* error.

**Testing**
- **StoreKit sandbox needs real hardware.** A simulator can only ever exercise the
  local `.storekit` file, which always returns three plans and proves nothing about
  App Store Connect. The **Mac app launched OUTSIDE Xcode** is the only local
  surface that hits the real store (`TIDBITS_PAYWALL=1`, now wired on macOS too).
- **An empty log is not a passing test.** A Gatekeeper dialog silently blocked the
  Mac app from launching at all and I nearly reported it as green. Screenshot.
